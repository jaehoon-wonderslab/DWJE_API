# AOI 원천 재확인 — `EDGE.dbo.TB_SAMSUN_COSMETIC` 실측 (2026-09-14)

WEB 세션 요청(요청 1·2·3)과 현업 지적「SEQ 가 많아봐야 100개인데 왜 2000~3,800 이지?」에 답하는 실측.
**발주자 지시: 앞으로 AOI 는 `TB_SAMSUN_COSMETIC` 만 쓴다.**

## 0. 결론 먼저

| 물음 | 답 |
| :--- | :--- |
| COSMETIC 이 AOI 인가 | **그렇다.** 외관 판정(`PASSED`)과 제품 최종 판정(`FINAL_PASSED`), 검사 항목명(`CATEGORY_STR`)이 있다 |
| 설비가 DIMENSION 과 같은가 | **완전히 다르다.** COSMETIC 은 `MN-*` 16대, DIMENSION 은 `GP-*`·`MQ-*`. 겹치는 설비가 하나도 없다 |
| 공정이 같은가 | 다르다. COSMETIC 은 `S135` C-LASER(**레이저**) · `S138` G-PACKING · `W160` C2-PACKING. DIMENSION 은 `S110` 도금 · `S120` 도장 |
| **현업 지적이 풀리는가** | **아니다.** COSMETIC 도 `SEQ` 가 1~4,452 다. 테이블을 바꿔도 100 이하가 되지 않는다 — 원인은 따로 있다(4절) |
| 한 행의 뜻 | **(제품 1개) × (검사 항목 1개)** 의 판정. DIMENSION 의 `FAI1~FAI100` 가로 전개를 세로로 편 모양이다 |
| 불량 유형이 있는가 | **있다.** 다만 절반은 `DF003` 같은 코드이고, 일부 설비만 `스크래치`·`얼룩`·`찍힘` 한글명을 쓴다 |
| 다른 서버인가(요청 3) | **아니다.** 같은 `192.168.7.203` · 같은 `EDGE` DB. `KPI` DB 에는 검사 테이블이 없고 `TNTWMS` 는 이 계정으로 접근 불가 |

## 1. 규모 — DIMENSION 보다 4.3배 무겁다

| 테이블 | 행수 | 크기 | 기간 |
| :--- | ---: | ---: | :--- |
| `TB_SAMSUN_COSMETIC` | **30,225,592** | 6,237 MB | 2026-07-31 ~ 2026-09-13 |
| `TB_SAMSUN_DIMENSION` | 6,960,138 | 7,464 MB | 2026-08-05 ~ 2026-09-12 |
| `TB_IAN_DIMENSION` | 1,294,154 | 1,248 MB | (미조사) |

인덱스는 DIMENSION 과 같은 모양 — 클러스터 PK `(WC_CD, EQPT_CD, LOT_NO, SERIAL_NO, …)` + 비클러스터 `SAMSUN_COSMETIC_DATE_TIME`.

일자별 행수: 09-08 972,765 · 09-09 1,058,490 · 09-10 1,258,211 · 09-11 2,455,530 · **09-12 3,144,557** (설비 13대). 증가 추세다.

## 2. 한 행이 무엇인가 — 제품 × 검사항목

09-12 하루: 행 **3,144,557** · `(WC,EQPT,LOT,SERIAL)` 키 **152** · 키+`SEQ` **458,076**.
→ `SEQ` 하나(제품 1개)에 평균 **6.87행**이 붙고, 그 행들이 검사 항목별 판정이다.

```
S135 MN-069 20260910 00022 SEQ=1535  DF003 PASSED=1
                              "      DF004 PASSED=1
                              "      DF007 PASSED=1
                              "      DF009 PASSED=0   ← 이 항목만 불량
                              "      DF021 PASSED=1
                              "      DF023 PASSED=1   FINAL_PASSED=1 (6행 모두 동일)
```

`CATEGORY_NUM` 은 유형 번호가 **아니라 그 항목의 측정값**이다 — `DF007` 은 값 종류가 2,895가지(0~725.222), `DF009` 는 2,627가지. 한글 항목에서는 `1.0`·`2.0` 처럼 검출 개수로 보인다.

## 3. 판정 두 개 — `PASSED` 는 항목, `FINAL_PASSED` 는 제품

한 `SEQ` 안에서 `FINAL_PASSED` 가 갈리는 경우가 **0건**(458,076 SEQ 전수 확인)이고, `PASSED` 가 갈리는 경우는 123,995건이다. 즉 확정이다.

| `PASSED` | `FINAL_PASSED` | 행수(09-12) | 뜻 |
| :--- | :--- | ---: | :--- |
| 1 | 1 | 2,592,817 | 항목 통과 · 제품 합격 |
| 1 | 0 | 409,128 | 이 항목은 통과했으나 **다른 항목 때문에** 제품 불량 |
| 0 | 1 | 50,976 | 항목은 불량인데 **제품은 합격** — 재검/오버라이드로 보인다 |
| 0 | 0 | 91,636 | 항목 불량 · 제품 불량 |

**제품(SEQ) 기준 09-12 집계:** 제품 458,076개 · 최종 불량 **73,109개(15.96%)**.
그중 항목 불량이 있는데도 합격 처리된 제품 50,976개, 반대로 항목은 전부 통과인데 최종 불량인 제품 80개.

> 화면의 불량률은 `FINAL_PASSED` 기준(제품 단위)이어야 한다. 행 기준으로 세면 항목 수만큼 부풀려진다.

## 4. 현업 지적 — 테이블 교체로 풀리지 않는다

09-12 키 152개의 `SEQ` 최대값 분포:

| 구간 | 키 수 |
| :--- | ---: |
| 1~10 | 1 |
| 51~100 | 1 |
| 101~1,000 | 3 |
| **1,000 초과** | **147** (최대 4,452) |

DIMENSION(최대 3,688)과 다르지 않다. **두 테이블 모두 `SEQ` 가 수천이다.**

발주자 정의는 「`SEQ`: 시리얼 번호 내 측정된 순」이고 실제 값도 그렇다(한 키 안에서 1부터 빈틈없이 증가). 그렇다면 어긋나는 것은 `SEQ` 가 아니라 **`SERIAL_NO` 의 입자**다.
`SERIAL_NO` 가 제품 1개가 아니라 **릴/트레이 단위**이고 그 안에 수천 개 제품이 들어 있다고 보면 두 테이블이 모두 설명된다. 현업이 「100 이하」라고 말한 단위가 무엇인지 확인이 필요하다.

또한 `SERIAL_NO`·`LOT_NO` 가 **빈 문자열**인 행이 상당수다(MN-065·066·067 등). 이 설비들은 키가 사실상 설비+시간뿐이다.

## 7. NAS 사진 키

COSMETIC 자체에는 사진 경로가 없다. 연결은 기존 `ax.tb_aoi_defect_image` 로 하며, 그 표의 키가
`(plant_cd, wc_cd, eqpt_cd, lot_no, serial_no, defect_cd, seq)` + `source_cd` 라 **COSMETIC 의 키 모양과 그대로 맞는다**
(`defect_cd` ↔ `CATEGORY_STR`, `seq` ↔ `SEQ`). `source_cd` 에 `COSMETIC` 값을 더하면 된다.
다만 현재 `seq` 가 `smallint` 라 **4,452 는 들어가도 32,767 을 넘으면 깨진다** — `integer` 로 넓히는 편이 안전하다.

## 9. `DF009` 는 불량 항목이 아니다 — 구현 중 찾은 것

첫 집계를 돌리자 S135 불량률이 99.5% 로 나왔다. 파고든 결과, `DF009` 의 `PASSED` 는 합부가 아니라 **값이 있는지**를 뜻한다.

## 10. 구현 — `/api/v1/quality/aoi/cosmetic/*` (2026-09-14)

메뉴 권한 `qc-aoi`. 마스킹: `qty` 없음 → 건수 null, `yield` 없음 → 비율 null.
**모든 비율의 분모는 제품 수이고 불량 판정은 `FINAL_PASSED` 다.**

### 10-1. `GET /summary?from&to&wcCd&eqptCd`

`wcCd` 는 **선택**이다(치수와 다르다 — 한계 세트가 없어 공정을 나눠 읽을 이유가 없다). 기간 상한 `app.aoi.cosmetic.max-days` 기본 **3일**.

### 10-2. `GET /items?from&to&wcCd&eqptCd`

화면 유형 필터용. 설비마다 항목 구성이 달라 전체 목록과 `byLine` 을 함께 낸다. 집계 캐시를 그대로 써 원천을 다시 읽지 않는다.
`itemNm` 은 `app.aoi.cosmetic.item-names` 에 이름이 있을 때만 채워진다 — 원천에 이름이 없다(발주자 확인). 비면 화면이 코드를 그대로 쓴다.

### 10-3. `GET /serials` · `GET /serials/{serialKey}`

목록 행: `serialKey`(`wc~eqpt~lot~serial`) · `prodCnt` · `prodNgCnt` · `ngRate` · `seqMin`/`seqMax` · `partial`(`seqMin > 1`) · `cavity` · `firstAt`/`lastAt`.
정렬 `prodNgCnt`(기본) · `ngRate` · `lastAt` · `firstAt` · `serialNo` · `prodCnt`. `size=0` 전량.

상세: 머리(`prodCnt` `prodNgCnt` `ngRate` `seqMin` `seqMax` `cavity`) + `items[{seq, finalPassed, measuredAt, cavity, checks[{itemCd,itemNm,verdict,value,passed}], ngItems[]}]`.
`only=ng`(기본) 최종 불량 제품만 · `all` 전 제품. **쪽 나누기는 제품(`SEQ`) 단위다** — 항목 행으로 자르면 한 제품이 두 쪽에 걸린다.
`ngItems` 에는 합부 항목만 담는다(`DF009` 제외). 잘못된 키 400, 없는 시리얼 404.

### 10-5. 걸린 것 두 가지 (다음 사람을 위해)

1. **임시 테이블은 세션에 매여 있다.** 문장을 나눠 보내면 JdbcTemplate 이 호출마다 풀에서 커넥션을 새로 얻어 `#c` 가 사라진다(오류 208). 적재·집계·정리를 한 문장열로 묶어야 한다.
2. **T-SQL 은 별칭이 테이블 힌트보다 앞이다.** `테이블 WITH (NOLOCK) d` 는 구문 오류 — JOIN 에 쓸 표기(`TABLE_ALIASED`)를 따로 뒀다.

같은 기간 인덱스 범위를 설비 수만큼 다시 훑으면서 시간이 설비 수에 비례했다.

| 이어서 `/serials` 또는 `/items` | 각각 다시 읽음 | **0.02초** (같은 스냅샷) |
| 목록 합 vs 집계 제품 수 | 488 어긋남 | **일치** (같은 스냅샷에서 나온다) |

집계·항목·시리얼 목록이 **한 번의 읽기**에서 나온다. 화면이 카드 세 개를 그려도 원천은 한 번만 읽는다.

**SQL 을 이 모양으로 만들기까지 세 번 틀렸다 — 다음 사람을 위해 남긴다.**

| 시도 | 결과 |
| :--- | :--- |
| `#c`(314만) ⋈ `#p`(46만) 를 인덱스 없이 조인 | **3분 초과.** 임시 테이블에 인덱스가 없어 플랜이 무너진다 |
| 윈도 함수로 조인을 없앰 | 24.6초. 되긴 하는데 적재도 32→46초로 늘어난다 |
| **`#p` 에 클러스터 인덱스(9초) 후 조인(7초)** | **16.1초.** 채택 |
| 파생 테이블 위에서 `OUTER APPLY` | **제한 시간 초과.** 옵티마이저가 제품마다 실행한다 → 시리얼 목록을 `#s` 로 실체화한 뒤 APPLY |

### 11-2. 직전 기간 비교를 선택제로 바꿨다 ([2] 관련)

검토 중에 드러난 것 — `/summary` 가 직전 동일 기간까지 **항상** 읽어 비용이 두 배였다(현재가 캐시에 있어도 64초).
`compare` 파라미터를 뒀다. 비우면 **직전 기간이 이미 보관돼 있을 때만** 낸다(공짜일 때만). 화면이 비교 카드를 펼 때 `compare=true` 로 부르면 된다.

웹 클라이언트 타임아웃이 45초라 첫 조회는 여전히 실패한다. 셋 중 하나를 골라야 한다.

| 안 | 내용 | 대가 |
| :--- | :--- | :--- |
| **(a) 화면 타임아웃을 늘린다** | AOI 화면의 이 호출만 90초 | 서버 변경 없음. 첫 조회 1분 대기 |
| (b) 캐시를 미리 덥힌다 | 서버가 오늘·어제 무필터 조회를 10분마다 미리 읽어 둔다 | 화면은 늘 0초. **원천을 주기적으로 읽으므로 발주자 승인이 필요하다** |

## 12. `PASSED` 극성 — 원천이 맞았다 (2026-09-14, 3차)

현업이 「웹이 `passed` 를 반대로 표기한다」고 지적해 원천을 확인했다. **원천도 API 도 맞았다.**
원인은 웹 클라이언트의 `EMPTY_FILTERS` 가 쿼리에서 `all` 을 지워 「전체 회차」를 눌러도 서버가 기본값 `only=ng` 로 답한 것이었다(WEB 세션이 찾아 고침).

**확인한 사실** — `S120~MQ-008~20260911~00040`:

| SEQ | 원천 `PASSED` | API `passed` |
| ---: | :--- | :--- |
| 1 | `0` | false |
| 2 | `1` | true |
| 3 | `0` | false |
| 4~10 | `1` | true |

`PASSED='0'` 771행 · `PASSED='1'` 3,005행 = 3,776. API 의 `failSeqCnt 771` · `seqCnt 3776` · `failRate 20.42` 와 모두 일치.
`PASSED` 는 `varchar(2)` 이고 표 전체 전 기간에 `'1'` 5,611,110 · `'0'` 1,486,007 두 값뿐이다(NULL·공백 없음).

**`'1' = 합격` 의 방증**

- DIMENSION 설비별 `'1'` 비율 60.70~87.13%. 뒤집으면 합격률이 13~39% 가 되어 양산에서 나올 수 없다.
- COSMETIC 제품 기준 `FINAL_PASSED=1` 84.04%.
- COSMETIC 에서 `CATEGORY_NUM=0` 이면 `PASSED=1`, 값이 있으면 `PASSED=0`(WEB 관찰) — 검출량이 0이면 합격.

**극성은 건드리지 않았다.**

### 12-1. 조용한 기본값을 없앴다

이 사건의 교훈은 **모르는 값을 조용히 기본값으로 되돌리면 안 된다**는 것이다. 화면이 `all` 을 잃어버렸는데도 서버가 200 을 주니
표의 판정이 전부 「불량」이 되었고, 그것이 극성이 뒤집힌 것처럼 보였다. 서버가 400 을 냈다면 그날 바로 드러났을 일이다.

COSMETIC 의 `only` 를 치수와 같이 고쳤다 — `ng`·`all` 만 받고 그 밖은 400 `E-VALID-001`(`field: only`). 대소문자·공백은 받아 준다.

```
GET …/cosmetic/serials/{key}?only=all        → only=all, meta.total 2,808 (전 제품, 양품 섞여 나옴)
GET …/cosmetic/serials/{key}?only=ng         → only=ng,  meta.total 874  (불량 제품)
GET …/cosmetic/serials/{key}?only=everything → 400 "only 는 ng 또는 all 입니다."
```

### 12-2. `/serials` 에는 `passed` 파라미터가 없다

WEB 이 `/cosmetic/serials?passed=all` 을 쓴다고 했는데 **서버에 그런 파라미터가 없다.** Spring 은 모르는 쿼리 파라미터를 조용히 무시하므로
지금은 걸러지지 않은 전체 목록이 그대로 나간다(우연히 `all` 의 뜻과 같아 증상이 없을 뿐이다).
`only`/`passed` 는 **시리얼 상세**에만 있다. 목록에 「불량이 있는 시리얼만」 거르는 기능이 필요하면 따로 만들어야 한다.
